# 传声筒 v1 方案

调研见 `docs/research/2026-11-06-tg-relay-bots.md`。

## 要什么

中文 Telegram 双向客服机器人：陌生人给机器人发消息，管理员在 Telegram 里回复，对方看不到管理员账号。比原项目（17sho/telegram-support-relay-bot）更安全、更不容易丢消息，部署只需要一个 Token。

## 假设（没问主人，按常见做法补的）

- 给谁用：个人或小团队，自己部署一个机器人，常见规模每天几十到几千条消息。
- 不沿用原项目代码结构，只借功能和验证思路；不做原数据库导入（原项目只有 8 star，用户少）。
- 对外发布与否由主人决定，代码按「公开也安全」写，目前只有私有备份仓库。
- 项目名「传声筒」，仓库沿用目录名 `tg-botsx`。

## 为什么重写而不是改

原项目问题集中在结构：两份实现、Webhook 无校验、每条消息反复建表、时间格式混乱（Python 存本地时间、当 UTC 显示）。逐处修等于全部重写。D1 和 SQLite 是同一种 SQL，所以一份 TypeScript 代码加两个薄运行层就够了，运行时零依赖。

## 关键设计

- **Webhook 校验**：`secret_token = HMAC(BOT_TOKEN, "webhook")`，不多存一个密钥；不对就 401。
- **串行处理**：`max_connections=1`，保证顺序，也避免并发建话题。一条坏更新不能堵队列，所以处理异常也返回 200，失败写日志，消息标 `failed` 由定时任务补发。
- **去重**：`seen_updates` 按 `update_id`。
- **认领**：设置页要求贴 Token 证明是部署者，再生成 10 分钟有效的一次性链接 `t.me/<bot>?start=claim_xxx`。点一下就成为管理员，不用查数字 ID。服务器版由命令行打印同样的链接。
- **免费额度**：一条普通消息目标不超过 12 次子请求，能合并的写入都走 `batch`（D1 把一次 batch 算一次查询）；迁移每个实例只查一次。
- **验证**：默认通过一次永久有效。点旧题、超时不算失败；连错 3 次锁 1 小时；验证前发的消息最多留 5 条，通过后补发。
- **拦截**：关键词、新联系人发链接、转发内容、新联系人人工审核。命中后进隔离区，`/filtered` 可放行，不直接丢。
- **防轰炸**：10 分钟内新联系人超阈值，进入 30 分钟防护并通知主人，可一键解除。
- **媒体组**：缓冲 1.5 秒后 `copyMessages`，保持相册。
- **失败反馈**：对方拉黑机器人时明确告诉管理员；发送成功只点 👌，不刷屏。

## 功能清单与验收

| 功能 | 验收（自动化测试场景） |
|---|---|
| 部署 | 伪造 Webhook 401；设置页 Token 错 403；认领链接一次性 |
| 私聊卡片模式 | 换人发新卡片；引用回复路由正确；未选中时提示 |
| 话题群模式 | 每人一个话题；话题被删自动重建；关闭自动重开；匿名管理员可回复；`//` 内部备注不外发 |
| 私聊话题模式 | 实验选项，无 `has_topics_enabled` 时拒绝开启 |
| 同步 | 编辑双向同步并保留原文；表态双向；`/del` 撤回 |
| 验证 | 全流程，含补发、旧题不计失败、锁定 |
| 拦截 | 进隔离区并可放行；屏蔽后静默 |
| 自动回复 | 欢迎语、收到回执、离线回复、关键词 |
| 管理 | `/list` `/search` `/history` `/note` `/block` `/stats` `/status` `/settings` |
| 群发 | 分批发送，额度内完成，出结果报告，可取消 |
| 数据 | 自动清理、`/cleanup`、`/export`、服务器版备份 |
| 运行环境 | Worker 用 miniflare 跑通；Node 用假 Telegram 跑通长轮询 |
